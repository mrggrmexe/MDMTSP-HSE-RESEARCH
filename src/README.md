# `src/` README

## Назначение

Каталог `src/` содержит исходный код вычислительного ядра проекта.

`src/` предназначен для:
- представления входных данных задачи;
- построения и валидации решений;
- вычисления целевой функции и производных метрик;
- реализации алгоритмов и операторов улучшения;
- интеграции solver-слоя с CLI / experiment pipeline;
- подготовки артефактов, используемых downstream-скриптами.

Документ описывает архитектурные роли подсистем `src/` в целом и не фиксирует конкретный состав уже реализованных эвристик.

---

## Архитектурные цели

Код в `src/` должен поддерживать следующие свойства:

- расширяемость: добавление новых алгоритмов без переписывания базовой инфраструктуры;
- воспроизводимость: детерминируемое поведение при фиксированном `seed`;
- разделение ответственности: данные, objective, validation, construction, improvement, orchestration;
- тестируемость: возможность unit/integration тестов на уровне модулей;
- нейтральность к experiment pipeline: C++-ядро не должно зависеть от Python-скриптов;
- переносимость: сборка через CMake, минимальные платформенные допущения;
- управляемая сложность: чёткие границы между слоями.

---

## Рекомендуемая верхнеуровневая структура

`src/` следует воспринимать как набор модулей по ролям, а не как плоский набор эвристик.

Рекомендуемая схема:

```text
src/
├── app/
├── common/
├── mdmtsp/
├── tsp/
└── <future modules>
```

Допускается дальнейшее расширение, например:
- `core/`
- `io/`
- `experiments/`
- `metrics/`
- `operators/`

Главное требование: новые каталоги должны отражать архитектурную роль, а не временное состояние реализации.

## Роли подсистем

### `src/app/`

Назначение:
- точка входа приложения;
- разбор CLI-аргументов;
- загрузка конфигурации;
- запуск solver pipeline;
- формирование stdout/stderr и JSON-артефактов результата.

`app/` не должен:
- содержать heavy algorithmic logic;
- дублировать objective/validation;
- знать внутренние детали конкретных операторов.

`app/` должен:
- собирать параметры в один run-context;
- передавать управление orchestration-layer;
- корректно обрабатывать ошибки пользователя и окружения.

Типовые обязанности:
- разбор `--algorithm`, `--instance`, `--seed`, `--output`, `--improve-iterations`;
- выбор зарегистрированного алгоритма;
- сохранение run-result в машиночитаемом формате.

---

### `src/common/`

Назначение:
- общие типы, утилиты и инфраструктурные компоненты;
- код, не привязанный жёстко к `tsp` или `mdmtsp`.

Типовые зоны ответственности:
- геометрия;
- расстояния;
- генераторы случайных чисел;
- общие контейнеры и helper types;
- общие ошибки / status objects;
- сериализация примитивных структур;
- утилиты времени и профилирования;
- файловые/path helper-ы;
- универсальные функции валидации аргументов.

`common/` не должен:
- зависеть от `app/`;
- зависеть от конкретных solver-стратегий;
- содержать доменно-специфичные эвристики.

---

### `src/tsp/`

Назначение:
- базовые алгоритмы и операторы, относящиеся к single-route / TSP-level логике.

`src/tsp/` должен содержать абстракции, которые применимы на уровне одного маршрута:
- route construction;
- intra-route local search;
- edge exchange operators;
- improvement heuristics;
- route cost delta evaluation;
- поддержка TSP-like solver-ядра.

Типовые компоненты:
- nearest neighbour;
- insertion heuristics;
- 2-opt / 3-opt / k-opt family;
- candidate-list logic;
- route normalisation;
- route feasibility on single tour level.

`src/tsp/` не должен:
- решать задачу многодепо orchestration самостоятельно;
- принимать решения о межмаршрутном перераспределении;
- зависеть от деталей suite/benchmark pipeline.

---

### `src/mdmtsp/`

Назначение:
- доменно-специфичный слой задачи нескольких коммивояжёров с несколькими депо;
- координация assignment, route construction и improvement на уровне полного решения.

Типовые зоны ответственности:
- представление MDMTSP instance;
- представление полного solution;
- assignment клиентов к депо / маршрутам;
- балансировка нагрузки;
- построение стартового решения;
- inter-route local search;
- глобальная objective evaluation;
- глобальная валидация ограничений;
- orchestration нескольких TSP-level процедур.

`mdmtsp/` является основным доменным слоем.
Он может использовать `tsp/`, но не должен растворяться в нём.

---

## Рекомендуемые логические слои внутри `src/`

Независимо от точной структуры каталогов, код должен распадаться на следующие логические слои.

### 1. Data model

Содержит структуры:
- instance;
- depot;
- customer;
- route;
- solution;
- move / operator result;
- run configuration;
- run result.

Требования:
- минимально избыточные структуры;
- явные инварианты;
- отсутствие скрытой мутации там, где это мешает reasoning;
- возможность сериализации.

---

### 2. IO layer

Содержит:
- чтение инстансов;
- запись run-артефактов;
- чтение/запись intermediate data при необходимости.

Контракт:
- IO-слой не должен принимать алгоритмических решений;
- ошибки IO должны быть отделены от ошибок solver-а;
- формат JSON/CLI-артефактов должен быть стабилен относительно experiment pipeline.

---

### 3. Objective layer

Содержит:
- вычисление стоимости маршрута;
- вычисление стоимости полного решения;
- delta-evaluation для move-операторов;
- дополнительные метрики качества.

Требования:
- единый источник истины для objective;
- отсутствие расхождения между тестами, validator-ом и solver-логикой;
- численная устойчивость;
- возможность быстрого инкрементального пересчёта.

---

### 4. Validation layer

Содержит:
- проверку корректности instance;
- проверку корректности route;
- проверку корректности полного solution;
- проверку соблюдения ограничений задачи.

Требования:
- validator не должен молча исправлять ошибки решения;
- validator должен возвращать диагностически полезную информацию;
- validation logic не должна дублироваться в нескольких несогласованных местах.

---

### 5. Construction layer

Содержит:
- initial solution heuristics;
- генерацию стартовых маршрутов;
- assignment-based decomposition;
- route seeding.

Требования:
- construction должен уметь работать независимо от improvement layer;
- стартовые решения должны быть воспроизводимыми;
- construction должен быть расширяемым для разных baseline-алгоритмов.

---

### 6. Improvement layer

Содержит:
- intra-route improvement;
- inter-route improvement;
- локальный поиск;
- metaheuristic shells;
- perturbation / intensification / diversification.

Требования:
- операторы должны быть композиционными;
- локальные улучшения должны иметь чёткие stopping criteria;
- необходимо поддерживать измерение вклада операторов и future ablation.

---

### 7. Orchestration layer

Содержит:
- верхнеуровневый pipeline solver-а;
- последовательность стадий:
  assignment -> construction -> improvement -> validation -> export.

Требования:
- orchestration не должен знать детали низкоуровневых move-операторов;
- должен быть возможен запуск разных конфигураций pipeline без переписывания ядра;
- ошибки стадий должны корректно пробрасываться вверх.

---

## Направление зависимостей

Рекомендуемое направление зависимостей:

```text
app
  -> mdmtsp
      -> tsp
      -> common
  -> common
```

Допустимые зависимости:
- `app -> mdmtsp`
- `app -> common`
- `mdmtsp -> tsp`
- `mdmtsp -> common`
- `tsp -> common`

Нежелательные зависимости:
- `common -> tsp`
- `common -> mdmtsp`
- `tsp -> mdmtsp`
- `app -> internal details of low-level operators`

Инвариант:
- dependency flow должен идти сверху вниз по уровню абстракции.

---

## Основные сущности, которые должны быть выделены явно

### Instance

Должна описывать:
- депо;
- клиентов;
- число коммивояжёров;
- геометрию/метрику;
- флаги постановки (`return_to_depot`, дополнительные ограничения и т.д.).

Требования:
- неизменяемость там, где это возможно;
- предвычисления (например, distance matrix) должны быть отделены от логической структуры instance.

---

### Route

Должен описывать:
- depot anchor;
- последовательность узлов;
- свойства маршрута (длина, нагрузка, feasibility cache, если нужен).

Требования:
- единая семантика маршрута для всей кодовой базы;
- чётко различать open route и closed route;
- избежать неявных соглашений о том, включён ли depot в `nodes`.

---

### Solution

Должна описывать:
- набор маршрутов;
- покрытие клиентов;
- распределение по депо;
- cached objective / derived statistics при необходимости.

Требования:
- solution должна быть валидируема независимо от алгоритма, который её построил;
- representation должна быть одинаково пригодна для baseline-ов и более сложных гибридных методов.

---

### Move / Operator

Оператор должен явно определять:
- preconditions;
- применяемый scope (route / pair of routes / global);
- результат применения;
- delta objective;
- whether move is improving / feasible.

Рекомендуется иметь общий контракт для operator-слоя, даже если конкретные реализации различаются.

---

## Стиль проектирования

### Интерфейсы

Нужно предпочитать:
- небольшие явные интерфейсы;
- сильную локальную ответственность;
- явные возвращаемые значения вместо скрытых побочных эффектов;
- именованные структуры результата вместо неочевидных tuple-like соглашений.

### Ошибки

Рекомендуется разделять:
- user/input errors;
- IO errors;
- invalid instance errors;
- invalid solution errors;
- internal logic errors.

Критические ошибки не должны маскироваться под “пустой результат”.

### Состояние

Нужно избегать:
- глобального изменяемого состояния;
- скрытых singleton-ов;
- implicit RNG;
- implicit caches без контролируемого жизненного цикла.

### RNG

Все стохастические части должны получать seed или RNG-context явно.

Инвариант:
- один и тот же instance + config + seed должны давать воспроизводимый результат.

---

## Требования к производительности

### Общие требования

Код в `src/` должен проектироваться с учётом:
- больших наборов клиентов;
- высокой стоимости полного пересчёта objective;
- ограничений по памяти;
- необходимости проводить массовые серии прогонов.

### Предпочтительные приёмы

- инкрементальный пересчёт objective, где это возможно;
- минимизация копирования больших структур;
- явный контроль precomputation;
- аккуратное использование `std::vector` и contiguous storage;
- отделение algorithmic complexity от diagnostic overhead.

### Нежелательные решения

- полные пересчёты без необходимости;
- тяжёлые debug-print в hot loops;
- несогласованные представления одного и того же решения в разных модулях;
- чрезмерное число transient allocations в operator-heavy коде.

---

## Согласование с downstream pipeline

`src/` должно быть совместимо с Python-слоем проекта.

Это означает, что C++-ядро должно уметь формировать артефакты, достаточные для:
- `aggregate_results.py`
- `plot_results.py`
- `visualize_solution.py`
- `export_excel_report.py`

Минимальные требования к export-слою:
- машиночитаемый run-result;
- стабильные поля metadata;
- корректный `instance_path` (предпочтительно repo-relative);
- сериализуемые маршруты;
- objective / feasibility / time metrics.

`src/` не должно зависеть от Python-реализаций этих скриптов, но должно соблюдать их контракт по данным.

---

## Рекомендуемая организация файлов

Документ не фиксирует точный набор файлов, но рекомендует следующий принцип.

### Заголовочные файлы

Должны содержать:
- публичные типы;
- интерфейсы;
- декларации алгоритмов;
- минимально необходимый inline-код.

### `.cpp` файлы

Должны содержать:
- реализацию;
- внутренние helper functions в анонимных namespace;
- локальную private logic, не являющуюся публичным API.

### Именование

Рекомендуется:
- один логический модуль = один основной заголовок + одна основная реализация;
- snake_case для файлов;
- имена файлов по архитектурной роли, а не по экспериментальному статусу.

Примеры ролей:
- `instance_io`
- `objective`
- `validator`
- `solution`
- `assignment`
- `interroute_local_search`
- `nearest_neighbour`

---

## Границы между TSP и MDMTSP

Важно сохранять различие:

### Что относится к TSP-уровню
- один маршрут;
- intra-route improvements;
- edge-based local search;
- single-tour construction;
- route-level objective deltas.

### Что относится к MDMTSP-уровню
- несколько депо;
- несколько коммивояжёров;
- assignment клиентов;
- баланс маршрутов;
- inter-route moves;
- выбор между несколькими route-level процедурами;
- глобальная feasibility.

Нарушение этой границы быстро приводит к хаотичной архитектуре.

## Расширение `src/`

### Добавление нового алгоритма

Новый алгоритм должен:
1. иметь чёткий `algorithm_id`;
2. жить в соответствующем модуле (`tsp/` или `mdmtsp/`);
3. использовать существующие objective/validation contracts;
4. быть зарегистрирован в app/orchestration layer;
5. быть тестируемым независимо от Python pipeline;
6. при необходимости экспортироваться в suite-config ecosystem.

### Добавление нового оператора

Новый оператор должен:
- явно указывать scope;
- использовать единый solution/route contract;
- поддерживать feasibility checks;
- быть пригодным для включения в future ablation.

### Добавление новой постановки / ограничения

Новая постановка должна по возможности добавляться:
- через расширение instance model;
- через validator/objective contracts;
- без размазывания conditionals по всему коду.

---

## Требования к тестируемости

Каждый логический слой должен быть покрываем тестами независимо.

Минимальные зоны тестирования:
- парсинг/загрузка instance;
- objective correctness;
- validator correctness;
- корректность route operators;
- корректность full-solution construction;
- корректность поведения на малых эталонных кейсах.

Unit tests должны проверять:
- инварианты данных;
- крайние случаи;
- согласованность objective и validation;
- воспроизводимость для фиксированного seed.

Integration tests должны проверять:
- полный solver pipeline на малых инстансах;
- стабильность run-result export.

---

## Инварианты `src/`

### Инвариант 1

Objective вычисляется единообразно во всех местах:
- solver
- validator
- tests
- exporter

### Инвариант 2

Любое решение можно проверить независимо от алгоритма, который его построил.

### Инвариант 3

Representation instance/route/solution не должна зависеть от конкретной эвристики.

### Инвариант 4

Все стохастические компоненты должны быть воспроизводимы при фиксированном `seed`.

### Инвариант 5

App-layer не должен содержать algorithmic core.

### Инвариант 6

Python pipeline должен получать достаточно данных из C++-ядра без необходимости реконструировать решение эвристически.

## Согласование с CMake

Каталог `src/` должен быть организован так, чтобы CMake мог:
- выделять библиотечные таргеты по логическим модулям;
- собирать отдельный executable для CLI;
- переиспользовать ядро в тестах без дублирования исходников;
- изолировать TSP-level и MDMTSP-level код в разные target groups при необходимости.

Рекомендуемый принцип:
- reusable core logic должна собираться как library target;
- `app` должен линковаться к этой библиотеке;
- tests должны линковаться к тем же library targets.

---

## Что не должно появляться в `src/`

Нежелательно хранить в `src/`:
- Python-скрипты;
- suite-конфиги;
- экспериментальные CSV/PNG/Excel;
- временные benchmark-артефакты;
- ad-hoc shell utilities;
- machine-specific absolute paths;
- код, завязанный на локальную файловую систему пользователя.

---

## Правила эволюции структуры

Так как `src/` будет модифицироваться, структура должна меняться по следующим правилам:

1. новые каталоги добавляются по архитектурной роли;
2. переименование модуля сопровождается обновлением CMake и тестов;
3. representation-инварианты фиксируются отдельно от конкретных алгоритмов;
4. новые solver-компоненты не должны ломать downstream data contracts;
5. перед объединением похожих модулей должно быть ясно, что они действительно принадлежат одному уровню абстракции.

---

## Минимальный рабочий путь данных

Обобщённый поток данных внутри `src/`:

```text
instance input
    -> instance model
    -> initial construction
    -> improvement pipeline
    -> solution validation
    -> objective evaluation
    -> run result export
```

---

## Использование `src/` как reference architecture

При разработке нового кода в `src/` каждый файл должен отвечать на вопросы:

1. к какому слою он относится;
2. от каких модулей он имеет право зависеть;
3. какие инварианты данных он предполагает;
4. какие структуры он читает и модифицирует;
5. должен ли он быть переиспользуемым в тестах;
6. должен ли он экспортировать данные для experiment pipeline.

Если ответы неочевидны, модуль либо расположен не там, либо объединяет слишком много ответственности.
